# Companion (Envoy / Flutter) — Vault Balance Discovery Relay

**Status:** design spec. The device side is implemented and compiling; this
document is the map for the **companion** side (the phone/desktop app that
holds the Tor/TCP connection to your Dojo and speaks BLE to the Passport
Prime). It is written to be implementable in any Flutter/Rust companion that
links `foundation-api` with the `envoy` feature.

> Cold signs, hot transmits — the device never opens a socket. This relay is
> how the *device* gets on-chain answers (vault balance / UTXO discovery)
> through the *companion's* network connection, exactly like the existing
> `BroadcastTransaction` path does in reverse.

---

## 1. What rides the wire

Two new `QuantumLinkMessage` variants were added in the
`OZARUMOTO/foundation-api` fork (branch `dojo-vault-5.7.0`, tag
`5.7.0-dojo-vault`):

| Variant | Tag | Direction | Payload |
|---|---|---|---|
| `ScripthashListUnspent` | `#[n(41)]` | device → companion | `{ scripthash: String }` |
| `ScripthashUtxos` | `#[n(42)]` | companion → device | `{ utxos: Vec<ScripthashUtxo> }` |

```rust
// api/src/api/bitcoin.rs (fork)
#[quantum_link]
pub struct ScripthashListUnspent {
    #[n(0)]
    pub scripthash: String,          // Electrum scripthash, hex
}

#[quantum_link]
pub struct ScripthashUtxo {
    #[n(0)]
    pub tx_hash: String,             // display (reverse) byte order, matches Txid::to_string()
    #[n(1)]
    pub tx_pos: u32,
    #[n(2)]
    pub value_sats: u64,
    #[n(3)]
    pub height: i64,                 // 0 = mempool, >0 = confirmed height
}

#[quantum_link]
pub struct ScripthashUtxos {
    #[n(0)]
    pub utxos: Vec<ScripthashUtxo>,
}
```

The wire codec is **CBOR** (`bc_envelope` / Gordian Envelope), and the
`#[quantum_link]` attribute macro expands per side:

- `keyos` feature (device): `Cbor` + `rkyv` derives
- `envoy` feature (companion): `Cbor` + `flutter_rust_bridge::frb(non_opaque)`
  — i.e. **FRB codegen turns these structs into Dart classes automatically**,
  no manual binding code needed.

Every message on the wire is wrapped in a sealed envelope
(`EnvoyMessage` from companion, `PassportMessage` from device) with:
- `QuantumLink::seal(...)` authenticated encryption (XID identity)
- ARID replay protection + 60-second expiration (`EXPIRATION_DURATION`)
- `PROTOCOL_VERSION` field

## 2. Companion-side receive path (FRB bridge case)

The companion already has an inbound BLE message pump that dechunks,
unseals, and decodes `QuantumLinkMessage`. The new variant flows through it
with **zero structural change** — only a new match arm.

```rust
// Companion Rust core (pseudo, mirrors os/quantum-link's dispatch)
match sealed.decode()? {
    QuantumLinkMessage::ScripthashListUnspent(req) => {
        let utxos = electrum_scripthash_list_unspent(&req.scripthash).await;
        let reply = QuantumLinkMessage::ScripthashUtxos(ScripthashUtxos { utxos });
        envoy_seal_and_send(reply).await?;   // EnvoyMessage envelope, as usual
    }
    _ => { /* existing arms */ }
}
```

On the Dart side (FRB-generated):

```dart
// flutter_rust_bridge generates: ScripthashListUnspent, ScripthashUtxo, ScripthashUtxos
final utxos = await api.handleScripthashListUnspent(req); // your bridge fn
```

The companion must **map the wire structs to Dart** via one thin FRB function
(e.g. `ScripthashListUnspent -> Future<ScripthashUtxos>`); the codec classes
are already generated by `frb(non_opaque)`.

## 3. The Electrum call

The scripthash is the key into the standard Electrum protocol method the
connected Dojo (electrs / Fulcrum / Dojo's bundled indexer) already speaks:

```
blockchain.scripthash.listunspent("39d6cf46...")  →  JSON-RPC 2.0
```

Each result item:

```json
{ "tx_hash": "3e7b...", "tx_pos": 1, "value": 250000000, "height": 872000 }
```

Companion mapping to the wire `ScripthashUtxo`:

| Electrum field | Wire field | Notes |
|---|---|---|
| `tx_hash` | `tx_hash` | keep as returned (display order) |
| `tx_pos` | `tx_pos` | `u32` |
| `value` | `value_sats` | `u64` |
| `height` | `height` | `i64`; 0 if unconfirmed |

**Connection:** the companion already holds the live connection to the user's
Dojo (Electrum server on plain TCP 50001, or via Tor). Use that same client —
do **not** open a new one per request. If the companion has no configured
node, or the query fails:

- Reply `ScripthashUtxos { utxos: [] }`? — **No.** Prefer an honest failure:
  drop the request and let the device-side 30-second pending-request timeout
  fire (`SendMessageError::Timeout`), so the app can tell the user "no node /
  query failed" instead of showing a fake zero balance. If your companion has
  a typed error channel, extend it later; the wire contract stays: **a reply
  is always a real answer, silence is failure.**

**Privacy (why this is safe):** the device computes the scripthash from its
own aggregate payment code and sends only the specific watch-window indices
the user refreshes (a *pull*). The companion never learns the payment codes
or the full vault address set — only the handful of scripthashes asked for.

## 4. The reply path (back to the device)

1. Build `ScripthashUtxos` from the Electrum results (or decide to stay silent
   on failure).
2. Wrap in `QuantumLinkMessage::ScripthashUtxos`.
3. Seal with the companion's identity + the paired device's XID, using the
   **same** `QuantumLink::seal` + `EnvoyMessage { timestamp, protocol_version }`
   path every other companion→device message uses (pairing responses,
   timezone responses, account updates, …).
4. Send over BLE (existing chunked send).

On the device, `os/quantum-link` matches the variant in `dispatch_ql_message`
and completes the pending `ScripthashListUnspent` archive request, returning
`Result<ScripthashUtxos, SendMessageError>` to the app. The app feeds the
UTXOs straight into `VAULT_UTXOS` → balance line, then the 4-round MuSig2
ceremony spends them.

## 5. Versioning / compatibility (read this before shipping)

- `PROTOCOL_VERSION` is currently `1`. Adding variants is additive at the CBOR
  level, but an **old companion that doesn't know tag 41/42 will fail to
  decode** the sealed message (the enum `TryFrom<CBOR>` has no catch-all for
  unknown tags).
- **Ship the fork to the companion in lockstep** with the device firmware. If
  you can't ship both at once, bump `PROTOCOL_VERSION` to `2` and have the
  companion reject version-mismatched envelopes cleanly (log + ignore) rather
  than crash the message pump.
- The device handler fails fast and honestly when unpaired
  (`SendMessageError::NoDevicePaired`), and the 30s timeout covers every
  silent-failure case, so the app always lands on the manual `txid:vout`
  fallback rather than a wrong balance.
